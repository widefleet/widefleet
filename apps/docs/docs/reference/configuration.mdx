App projects use `wrangler.jsonc`. Start with the generated starter and use the
supported fields below. The CLI validates the configuration and rejects unknown fields.

## Minimal app configuration

The SvelteKit starter builds the Worker and assets at the paths shown here:

```jsonc
{
  "name": "my-app",
  "main": "build/worker.js",
  "compatibility_date": "2026-10-01",
  "compatibility_flags": ["nodejs_compat"],
  "assets": { "directory": "build/public", "binding": "ASSETS" },
}
```

The TanStack Start starter uses `build/server/index.js` as `main` and the same
`build/public` asset directory. Its Vite configuration selects `src/server.ts`
as the source entry during development and build. Keep the generated Wrangler
configuration pointed at the built entry for `widefleet deploy`.

The included notes app also needs its generated `DB` and `FILES` bindings. Keep
those declarations while using that example; the minimal configuration above is
for app code that does not use storage.

| Field                                 | Meaning                                                                                                                                                                       |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`                                | App identifier within the selected installation. Use 1–48 lowercase letters, digits or hyphens, starting with a letter and ending with a letter or digit. `auth` is reserved. |
| `main`                                | Built Worker entry module, relative to the configuration file.                                                                                                                |
| `compatibility_date`                  | Worker compatibility date; see [runtime compatibility](/reference/runtime-compatibility) for supported APIs.                                                                  |
| `compatibility_flags`                 | Supported flags are `nodejs_compat` and `nodejs_als`; see [Node.js compatibility](/reference/runtime-compatibility#nodejs-compatibility).                                     |
| `assets.directory` / `assets.binding` | Built static asset directory and the binding exposed to app code.                                                                                                             |
| `vars`                                | Plain-text string values. Never put credentials here.                                                                                                                         |

Service entrypoints come from the Worker module exports; there is no additional
service declaration in `wrangler.jsonc`. Workflow classes declared in `workflows`
are excluded from the service catalog. A Worker with only named service exports
and no `assets` has no browser URL. See [app services](/guides/app-services).

Changing `name` selects another app on the next deployment. It does not rename an
existing app or move its data. The CLI uses your saved or company-provided
platform URL to select the installation; see [CLI configuration](/reference/cli-configuration).

## Resources

| Configuration                           | Resource                                                                                                                                               |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `d1_databases`                          | D1 database bindings with `binding`, `database_name` and optional `database_id` and migration settings.                                                |
| `r2_buckets`                            | File storage bindings with `binding` and `bucket_name`.                                                                                                |
| `kv_namespaces`                         | Key-value bindings with `binding` and `id`.                                                                                                            |
| `queues.producers` / `queues.consumers` | Queue producers and Worker queue handlers.                                                                                                             |
| `triggers.crons`                        | Schedules delivered to an exported `scheduled` handler.                                                                                                |
| `workflows`                             | Named Workflow classes with `binding`, `name` and `class_name`; requires CLI and platform `0.3.0` or newer and a runtime advertising Workflow support. |

Resources are scoped to each app or preview. Keep resource identifiers stable to
preserve access to existing data. Native data remains after a declaration is removed.
For Cron, Queue or Workflow handlers, export them from a custom entry module
alongside the generated starter's HTTP handler.

### Queue deployment availability

Cloudflare installation operators can set `queues: false` in the hosted installation
profile to reject app deployments with Queue producers or consumers. The setting
defaults to `true` and belongs to the installation profile, not the app's `wrangler.jsonc`.

If deployment reports `Queues are disabled for this installation`, remove the Queue
declarations and code that requires them, or ask your installation operator to enable
Queues. Rollbacks to artifacts that use Queues are also rejected. Existing apps keep
running, and the setting does not delete Queue data or pause existing consumers.

### Dynamic Worker execution limits

With Widefleet **0.5.0 or newer**, Cloudflare installation operators can set CPU
and subrequest budgets in the versioned installation profile, then deploy it
through their normal deployment process. For example:

```json
{
  "executionLimits": {
    "http": { "cpuMs": 100, "subRequests": 50 },
    "service": { "cpuMs": 250, "subRequests": 50 },
    "cron": { "cpuMs": 1000, "subRequests": 200 },
    "workflow": { "cpuMs": 5000, "subRequests": 500 },
    "readiness": { "cpuMs": 100, "subRequests": 10 }
  }
}
```

Choose budgets for your workloads; these values are examples. When configuring
`executionLimits`, supply all five profiles with a positive integer `cpuMs` and
a nonnegative integer `subRequests`. Omitting `executionLimits` keeps the
platform's existing limits.

| Profile     | Applies to                                                                                            |
| ----------- | ----------------------------------------------------------------------------------------------------- |
| `http`      | Each app HTTP invocation that executes Worker code.                                                   |
| `service`   | Each HTTP or RPC invocation through a granted app connection.                                         |
| `cron`      | Each app's scheduled invocation.                                                                      |
| `workflow`  | A Workflow runner invocation, shared across its steps rather than a lifetime budget for the workflow. |
| `readiness` | App and Workflow readiness checks.                                                                    |

CPU time measures active computation, excluding time spent waiting for network
or storage. Cloudflare ends an invocation that exceeds its CPU or subrequest
budget. Static asset serving and Queue consumers keep their existing limits;
these profiles control Dynamic Worker execution rather than total service costs.

Changes apply to new invocations, including cached Workers. Running invocations
keep their selected budget. These are installation settings; app `wrangler.jsonc`
files use the operator's limits.

If an invocation exceeds its budget, check its runtime logs, reduce the work per
call or ask the operator to adjust that profile. See
[Cloudflare's Dynamic Worker limits](https://developers.cloudflare.com/dynamic-workers/usage/limits/)
for runtime constraints.

## Database migrations

Apply SQL migrations separately from deployment using the CLI's migration commands.
Follow [database migrations](/guides/migrations)
for file configuration, Drizzle, first-schema deployment and failure recovery.

## Settings outside this file

Manage company SSO, app access groups, network grants and app connections through
the management UI or the relevant [CLI commands](/reference/cli). These settings
remain in effect across code deployments and rollbacks.

After changing app configuration, [publish a preview and verify it](/guides/deployments).
